How each estimate was reached

1. Problem understanding & user fit: 9 / 10.

  • The login card states the problem in plain words: mismatches, duplicates, missing approvals.
  • A "Why we built this" banner now sits on the clerk home and the PlantPay home.
  • Each role has its own welcome banner with live figures: clerk (hours saved, exceptions with owner), approver (items waiting, value, oldest age), supplier (open invoices, cleared vs on hold).
  • Gap: the supplier and approver pages show measured counts, but not a measured "wait reduced from X to Y days". The baseline is an assumption.

2. Innovation & original thinking: 9 / 10.

  • All features already existed and work: Root-Cause Resolver, Counterfactual ("would pass if PO price were ₹412"), Process-Mining Twin, Relationship Graph, Supplier Intelligence (three separate scores), four predictive models, Payment Readiness Passport.
  • New Innovations page lists 10 features, each with a "See it live" button and a Rule-based or AI-assisted label, so judges can count them.
  • Gap: the graph can be focused on a vendor but is not drag-interactive.

3. Working prototype: 18 / 20 (highest weight).

  • Evidence: production smoke test passed 786 of 786 checks, 0 failures, 0 crashes. It covers the full workflow (supplier, clerk, approver, audit), all demo documents, planted cases, outage handling, and the Golden Journey three times in a row (25 of 25 each).
  • Duplicate INV-6120R is caught before approval; the chatbot answers from live records; the controls report renders.
  • Unit tests: 443 of 444. The one failure is a pre-existing clock dependency in a test (it hard-codes 12-Nov, and the real date is now 13-Nov). It does not affect the app.
  • Why not 20: no human browser click-through yet; the Predictions page takes about 2 to 5 seconds when cold, above the 3-second target on the first load; first start on a clean clone takes about 11 seconds.

4. Technical design & architecture: 8.5 / 10.

  • New Architecture page: six-database diagram, 3-bullet data flow, "how the integration layer works" (connectors, canonical model, event stream, REST facade), live source health.
  • Rule-based and AI-assisted labels on the feature pages make the separation of concerns visible.
  • API reference page lists every endpoint. Swagger-style interactive docs were not built.

5. Feasibility & scalability: 8 / 10.

  • Production-readiness section with five points: database swap, horizontal scaling, authentication, audit compliance, connector extensibility.
  • Outage toggle is tested: taking any one of the six sources offline does not crash the pipeline (76 of 76 outage checks pass).
  • Models are saved to disk (data/ml/models.json) and loaded once per process; evaluations are stored.
  • Capped because scalability is argued by design. The demo runs on SQLite and was not load-tested.

6. Business / user value & impact: 12 / 15 (second highest weight).

  • Dashboard and the controls report now show: value of possible duplicates held back, invoices matched clean and clerk hours saved, exceptions that arrived with a root cause and owner, value blocked from payment.
  • "What would happen without PlantPay?" before/after table added.
  • Counts and rupee values are measured from the synthetic demo data. The time comparisons rest on three assumptions, marked "assumption" on screen: 12 minutes per manual check, 3 days to find a root cause, 5 working days for a supplier reply.
  • Gap: no real Plant X figures exist, so judges may discount the time savings. This is the largest remaining gap.

7. Responsible AI, security & data: 9 / 10.

  • Already in place: unverified-prediction labels, "warning, not proof" on risk flags, "requires independent verification" on bank changes, hash-chained audit trail with a Verify button, role-based access (suppliers see only their own invoices), API requires a key or session (401 otherwise).
  • New: Responsible AI page with nine commitments, and Rule-based / AI-assisted labels on feature pages.
  • Gap: labels are on the main feature pages, not on every single output.

8. User experience & accessibility: 4 / 5.

  • Consistent dark design system, colour-coded status chips with shapes (not colour alone), friendly empty states, no horizontal overflow at 900 px, no raw errors in the smoke test.
  • Spinners only on the dashboard and audit pages. Adding them everywhere made "not found" pages return HTTP 200 and weakened the supplier-isolation check, so we kept them to routes where that is safe.
  • Skeleton loaders, side drawers and animated gauges were left out because of the code freeze.

9. Presentation & demo: 4.5 / 5.

  • Golden Journey (nine steps, Back/Next and arrow keys, presenter notes with a timer, automatic fallback to pre-computed results, feature badges, closing checklist) already existed and passes three runs.
  • New DEMO.md has the exact click path, what to say, what to point at, and a fallback plan.
  • Not yet rehearsed against a stopwatch on the venue laptop.

10. Q&A & team understanding: 4.5 / 5.

  • DEMO.md has a Q&A cheat sheet: the six required questions plus six more (impact-number sources, ML evidence, supplier data isolation, API protection, extraction errors, GenAI use).
  • Rule: every member must be able to explain all code, and GenAI use must be declared. A cheat sheet does not replace that.
